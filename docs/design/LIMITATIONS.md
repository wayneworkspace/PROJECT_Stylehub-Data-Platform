# Limitations

This is the complete list. The README shows only the biggest ones.

| Area | Limitation |
|---|---|
| Testing | Run `uv run pytest` for the unit tests. dbt (the old 12-model layout), the Raw and Bronze steps and an earlier version of the Airflow DAG have run on a real BigQuery project. On 2026-10-16 the Bronze load into one partition per day (`WRITE_TRUNCATE`), the retry helper, Silver (50 nodes: 13 models and 37 tests) and Gold (34 nodes: 6 models and 28 tests) ran on real BigQuery and all passed. The incremental `fact_events` scanned about 2.7 GiB. The Bronze tables were first dropped and rebuilt from Raw, because they were an old version without partitions. The new DAG operators, the merged compose file in a running Airflow and the freshness check have not run there yet. Gold numbers were not checked by hand against the CSV files. |
| Schema | `EXPECTED_SCHEMAS` covers the four course tables as BigQuery detected them. New columns only give a warning. `shipments` has no source, so `fact_shipments` is built from order dates (shipped orders only). |
| Setup scripts | `setup_gcp` and `load_csv` have run on a real project. BigQuery detects column types from the CSV, so check them again if the files change. |
| Sources | The pipeline reads the course tables that `load_csv` put in BigQuery. Postgres and API ingestion were removed (never run on a real source). |
| Watermark | Not used for CSV data (no `updated_at`). Every run reads whole tables. |
| Deletes | The pipeline cannot see rows that the source deletes. |
| Scheduling | Airflow runs the DAG once a day. Each task retries once after 5 minutes. dbt also retries a BigQuery job that fails for a short time, up to 3 times (`job_retries` in `dbt/profiles.yml`). After that, a failed step stops the run until the next day or a manual run. |
| Run history | Only `run_daily` writes to `pipeline_runs`. If BigQuery is down, the row waits in `logs/pipeline_runs_pending.jsonl` and goes with the next row. In a throwaway container that file is lost with the container. Only the Bronze step counts rows. |
| Alerts | One Discord message per failed step. `check_freshness` (a GitHub Actions schedule) alerts when no good run happened in 26 hours. It needs a one-time setup and has not run yet. |
| Retries in Python | `retry.py` retries short BigQuery and GCS errors up to 5 times (waits of about 2, 4, 8 and 16 seconds, so about 30 seconds in all; a longer outage still fails the step). Permission, missing table and bad SQL errors fail at once. It is tested with fakes only. |
| VM | Airflow runs on a laptop in Docker. It has not run on a GCP VM yet. |
| Docker | The new CD pushes the image CI built, with the commit-id tag only. CD signs in with Workload Identity Federation and pushes the image to Artifact Registry. A run on GitHub was green. The image has not run on a VM yet. |
| Rebuilds | Silver and Gold tables are rebuilt in full on each run, except `fact_events`, which is incremental. |
| Events | `fact_events` rebuilds the newest 3 days (`events_lookback_days`), so late events inside that window are kept. Later ones are missed until a `--full-refresh`. The first run (or `--full-refresh`) scans about 13 GB. There is no `dim_date` yet. The event dates (2019) do not overlap the order dates (2024 and later). |
| Bronze copies | Each new day adds one snapshot of every table. Snapshots expire after 30 days. `events_raw` (a 15 GB copy) is dropped by the events bootstrap unless you pass `--keep-raw`. |
| CI | The rewritten workflows (SHA-pinned Actions, Trivy, pip-audit, SBOM, CI-to-CD image hand-over) have not run on GitHub yet. actionlint and shellcheck found nothing in the workflows and `run_on_vm.sh`. The base images of both Dockerfiles are pinned by digest (read on 2026-10-16). |
| Service accounts | One VM per job with an attached account is designed in `docs/ops/DEPLOY_VM.md` (no key files). Not run on a real VM. On a laptop one key still does everything. |
| Backups | Bucket versioning is set when `setup_gcp` creates the bucket (and by one `gcloud` command for an old bucket). BigQuery tables have no extra backup beyond time travel. |
| Dependencies | `uv.lock` pins exact versions. Update them on purpose with `uv lock --upgrade`. |
| Cost guard | Every BigQuery query has `maximum_bytes_billed` (default 50 GB, about three times the biggest query, `BQ_MAX_BYTES_BILLED`). A legit big query may need a higher limit. |
| Settings and clients | Library functions take an optional `cfg` (Settings) and `client`, so tests and other callers pass their own (`load_day`, `extract_full`, `copy_events`, `run_layer`, `render_sql`, `query_config`, `dbt_environment`, `last_complete_run`, ...). Only the command-line entry points read the environment, through `settings()`. A function called without them still builds its own BigQuery or GCS client. `ROOT` is found from the file path, so the package must stay inside the project folder (Docker and Airflow do this). |
| Untested on BigQuery | Partition expiry (30 days have not passed yet) and the cost limit refusing a query that is too big. The latest-snapshot macro, `_PARTITIONDATE` and the partitioning of `fact_order_items` ran on 2026-10-16. |
| Scale | A learning project that uses a course dataset. Do not use it for real business reports. |
| Data date label | `--date` is only a label for the folder. The CSV source is read as it is TODAY, so a back-dated run does not rebuild the past. `run_ingest` warns when the label is more than 3 days old. |
| Partition expiry | Bronze partitions expire after 30 days. `load_bronze` warns if you load a day older than that, because BigQuery may delete the partition. |
| Silver and Gold | They are replaced in place by `dbt build`. There is no Write-Audit-Publish as in Bronze; dbt tests run in the same build. |
| Airflow tasks | One task per step. A failure in the middle of `bronze` re-runs all four tables. |
| `fact_events` | It is incremental, but the data is static, so the incremental path is not proven by new data. |
| Infrastructure as code | `infra/terraform/` describes the bucket, datasets, service accounts, image repository and the GitHub login (Workload Identity Federation). Applied to the real project on 2026-10-16: `plan` said 0 to destroy, `apply` imported 11 existing resources and added 39, and a second `plan` said no changes (see [TERRAFORM.md](../ops/TERRAFORM.md)). It was not tried on a fresh project, and the state is one local file. The VMs, the firewall and the `pipeline_runs` table are not in it, and CI does not check the Terraform files. |
| Airflow version | The project runs Airflow 3.3.2 (the DAG loads and its 10 DAG tests pass in a real 3.3.2 install; on 2026-10-16 the Docker image was built, `docker compose up` started the five containers, and `airflow dags test stylehub_daily 2026-10-15` ran all six tasks to success on real GCS and BigQuery, Silver 50/50 and Gold 38/38). NOT run yet: a run started by the scheduler itself at 02:00 UTC, the login with the password file, and the Discord alert from Airflow (the test used `--no-alert`). The base image is pinned by digest (read on 2026-10-16). Airflow 3 login uses the Simple Auth Manager with one admin user, meant for a local container, not for a shared server. |
| Latest-snapshot macro | The pipeline reads the newest Bronze day of each table ONCE per dbt run (`run_dbt.bronze_snapshot_dates`), passes it as the variable `bronze_snapshot_dates` and saves it in `pipeline_runs.detail`, so one run reads one snapshot. Run by hand without the variable, the macro looks the day up at compile time, and `dbt compile` then needs a BigQuery connection. A `*_latest` view in Bronze was not built: a view that picks the newest day with a subquery or join may scan every partition, and that could not be measured without BigQuery. |
| CI runs no model | `dbt-ci.yaml` runs the models, tests and unit tests on BigQuery only when the repository variable `WIF_CI_SERVICE_ACCOUNT` is set (`terraform output` prints the values). Until then CI checks `dbt parse` and the SQL style, not the numbers. The variable was set on 2026-10-16, but the job has not run on GitHub yet. |
| Contracts and unit tests | Five Gold tables have `contract: {enforced: true}` with column types, and four dbt unit tests protect the revenue, profit, funnel and return-rate rules (`_reporting__unit_tests.yaml`). They ran on BigQuery on 2026-10-16 (Gold: 38 nodes passed). The funnel test compares only the three counts, not the two rates. dbt still warns that `numeric` has no precision (write `numeric(38,9)` to silence it, not tried). `daily_events_by_type` has no contract (incremental, insert_overwrite). Silver has no contract and no unit test. |
| Ingestion is not fully raw | `type_empty_columns`, dropping `users.user_geom` and `--on-schema-change absorb` change the data before it reaches Raw. They keep the Parquet types stable day to day. |
| Data path | The source is in BigQuery (US) and Raw is in GCS (`asia-southeast1`), so a table is read with pandas and written as Parquet. This is simple and fine for the four small tables. A table of many GB would need an extract job in one region. |
| Logging | Every command-line step uses `logging` (`common/logs.py` prints the message only, on stdout). No `print` is left in the package. |
| Type stubs | `requests` is type-checked (`types-requests`). `pandas`, `pyarrow` and the Storage client are still skipped by mypy: `pandas-stubs` was not added because it may need many code changes. |
